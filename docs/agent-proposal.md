1. AI 업무 비서 (Work Copilot)

우선순위 최상

자연어로 요청하면 Jira의 프로젝트와 이슈를 검색하고 분석해 업무를 처리합니다.

- "이번 주 내가 해야 할 일 정리해 줘."

- "A 프로젝트가 지연되는 이유 알려줘."

- "회의 내용을 바탕으로 이슈를 만들어 줘."

- "이 이슈를 완료하려면 다음에 뭘 해야 해?"

핵심: 사용자가 Jira의 복잡한 메뉴와 검색 조건을 몰라도 업무를 수행할 수 있게 합니다.

2. 프로젝트 리스크 예측 Agent

우선순위 최상

이슈, 스프린트, 의존성, 작업 이력 등을 분석해 문제가 발생하기 전에 알려줍니다.

- 일정 지연 가능성이 높은 이슈 탐지

- 병목 구간 및 과부하 담당자 발견

- 선행 작업 지연에 따른 연쇄 영향 분석

- 프로젝트 완료일 및 릴리스 위험 예측

핵심: 현황을 보여주는 대시보드에서 미래의 문제를 예방하는 시스템으로 전환합니다.

3. 업무 실행 Agent

분석에 그치지 않고 실제 Jira 작업을 수행합니다.

- 이슈 생성 및 설명 작성

- 적절한 담당자와 컴포넌트 추천

- 라벨, 우선순위, 상태 업데이트

- 하위 작업 및 의존성 생성

- 반복적인 업무 절차 자동 실행

예를 들어 "이번 릴리스의 보안 점검을 준비해 줘"라고 하면 필요한 체크리스트와 하위 작업을 만들고 담당자 후보까지 제안합니다.

핵심: 조회형 AI에서 실행형 AI로 발전합니다. 중요한 변경은 사용자 승인 후 실행하도록 설계합니다.

4. 회의·문서 → 업무 자동 변환

회의록, 이메일, 요구사항 문서, 고객 피드백을 실행 가능한 업무로 변환합니다.

- 요구사항과 수용 기준(Acceptance Criteria) 추출

- Epic → Story → Task 자동 분해

- 담당자, 일정, 의존성 후보 생성

- 중복 이슈 탐지

- 기존 이슈와 관련 문서 연결

핵심: 업무가 시작되기 전의 수작업을 줄이고, 문서와 실제 실행 간의 단절을 해소합니다.

5. 사내 업무 지식 Agent

Jira 이슈뿐 아니라 Confluence, 사내 문서, 기술 문서, 과거 장애 기록 등을 연결합니다.

- "비슷한 장애가 과거에 있었나?"

- "이 기능의 설계 결정 근거는?"

- "이 API를 변경하면 어떤 서비스에 영향이 있나?"

- 관련 문서와 담당 전문가 추천

핵심: 단순 키워드 검색이 아니라 업무 맥락과 관계를 이해하는 지식 시스템을 구축합니다.

6. 개발 생산성 Agent

개발 워크플로와 연결해 코딩부터 테스트까지 지원합니다.

- 이슈 기반 코드 변경안 및 PR 초안 생성

- 테스트 케이스와 회귀 테스트 추천

- 버그 원인 및 관련 코드 후보 분석

- PR 리뷰 요약과 변경 영향 분석

- 배포 후 오류와 관련 이슈 연결

핵심: Jira를 개발 생명주기 전체를 연결하는 업무 허브로 만듭니다.

7. AI 리포팅 및 의사결정 Agent

보고서를 작성하는 데 그치지 않고 의사결정에 필요한 원인과 선택지를 제공합니다.

- 주간·월간 보고서 자동 작성

- 계획 대비 실적 및 변동 원인 분석

- 팀별 업무량과 병목 분석

- 일정·범위·인력 변경 시나리오 비교

- 경영진 질문에 근거를 붙여 답변

핵심: 보고서 작성 시간을 줄이고 관리자가 문제 해결과 의사결정에 집중하게 합니다.

8. 멀티 Agent 협업

여러 전문 Agent가 하나의 업무를 나누어 처리합니다.

- 기획 Agent: 요구사항 분석

- 개발 Agent: 구현 작업과 기술 의존성 분석

- QA Agent: 테스트 및 품질 검토

- PM Agent: 일정과 리스크 관리

- 운영 Agent: 배포와 장애 대응 준비

핵심: 하나의 거대한 AI가 모든 것을 처리하는 방식보다 역할별 전문 Agent를 조합해 복잡한 업무를 완성합니다.

# 검토 — innoFlow 에 적용할 수 있나 (2026-10-15)

위 8개는 Jira 를 전제로 한 제안이다. innoFlow 는 **안건(정해야 할 것) · 이력(결정 · 미룸)** 이 중심이고,
작업은 그 결정에 걸려 움직인다. 그 차이를 놓고 하나씩 봤다.

## 지금 서 있는 자리

- **이미 있는 것**
  - 챗봇(Claude 도구 루프) — 읽기 도구 7개(`search_threads` · `get_thread` · `search_tasks` · `get_task` ·
    `list_tasks` · `find_similar_tasks` · `list_members`)와 쓰기 초안 1개(`propose_tasks`)
  - **초안 → 사람이 [등록]** 흐름 — 챗봇은 직접 저장하지 않는다. 3번이 말하는 '승인 후 실행' 이 이미 있다
  - Jira 에 없는 데이터 — 안건의 결정 기한 · 미룸 횟수와 사유 · 작업 상태 '막힘' ↔ 안건 연결
  - 사용자의 경력 · 기술 스펙(`member.career` · `member.skills`), 파트
- **빈 곳**
  - 챗봇이 **누가 묻는지 모른다** — 프롬프트에 오늘 날짜만 들어간다. "내 할 일" 에 답하지 못한다
  - `list_members` 는 id · 이름만 준다 — 기술 스펙을 담당자 추천에 못 쓴다
  - 작업끼리의 **선후 의존성이 없다** — 상위 ↔ 하위, 작업 ↔ 안건만 있다
  - **작업 상태 변경 이력이 없다** — 안건 이력은 남지만 작업이 언제 막혔는지는 모른다

## 하나씩

| # | Agent | 판단 | 이유 |
| --- | --- | --- | --- |
| 1 | AI 업무 비서 | **바로 적용 (작게)** | 대부분 있다. 묻는 사람(`member_id`)을 프롬프트에 넣고 '내 작업 · 내 안건' 도구 하나면 "이번 주 내 할 일" 이 된다 |
| 2 | 리스크 예측 | **최우선 — '결정 병목 리스크' 로 바꿔서** | 일정 예측은 의존성 · 상태 이력이 없어 근거가 약하다. 대신 **결정이 미뤄져 일이 막히는 것** 은 지금 데이터만으로 계산된다. 이 제품을 만든 이유와 같다 |
| 3 | 업무 실행 | **넓혀서 적용** | `propose_*` 패턴을 넓힌다 — 기술 스펙 기반 담당자 추천, 안건 초안, 상태 · 담당자 일괄 변경 초안 |
| 4 | 회의 · 문서 → 업무 | **적용 — README 의 처음 의도** | 회의록을 붙이면 **안건 초안(결정 · 미룸 이력 포함) + 작업 초안** 으로 나눈다. 중복은 `find_similar_tasks` 를 다시 쓴다 |
| 5 | 사내 업무 지식 | **부분 적용** | 프로젝트 안의 "과거에 비슷한 결정" 까지. Confluence · 장애 기록 연동은 범위 밖이다. `server/PLAN.md` 7-4 의 "이 안건을 정하려면 뭘 체크해야 하나" 가 여기다 |
| 6 | 개발 생산성 | **제외** | 코드 저장소 · PR 연동이 필요하다. 업무 · 결정 관리라는 방향에서 벗어난다 |
| 7 | 리포팅 · 의사결정 | **적용 (2번 다음)** | 주간 보고를 "이번 주 정해진 것 / 미뤄진 것 / 그래서 막힌 작업" 으로 — 이 제품만 쓸 수 있는 보고서다. 2번의 계산을 다시 쓴다 |
| 8 | 멀티 Agent | **보류** | 지금 규모는 도구 하나의 루프로 충분하다. 비용 · 복잡도만 는다 |

## 순서

1. **결정 병목 리스크** (2번 변형) — 새 데이터 없이 효과가 가장 크다.
   계약 초안 `docs/api/risk.md` · 순서 `server/PLAN.md` 10단계 · `web/PLAN.md` 11단계
   - 기한이 지났는데 안 정해진 안건, 여러 번 미뤄진 안건, 오래 손 안 댄 안건
   - 그 안건이 막고 있는 작업과 하위 작업 수(연쇄 영향), 결정 전에 기한이 오는 작업
   - 이미 정해졌는데 아직 '막힘' 인 작업, 걸린 안건 없이 '막힘' 인 작업
   - 사람별로 안 정해진 안건 · 막힌 작업이 몰린 정도
2. **묻는 사람 인식 + 담당자 추천** (1 · 3번) — 프롬프트에 묻는 사람, `list_members` 에 기술 스펙 · 맡은 작업 수
3. **회의록 → 안건 + 작업 초안** (4번) — `propose_threads` 를 더하고 초안 → [등록] 흐름을 그대로 쓴다
4. **주간 결정 리포트** (7번) — 1번의 계산을 다시 쓴다

**먼저 깔아 둘 것** — 일정 예측까지 가려면 **작업 상태 변경 이력(`task_log`)** 이 있어야 한다.
지금부터 쌓아야 나중에 쓸 수 있다.

오른쪽 아래 팝업. Claude 가 도구를 골라 부르며 답하고, 답 안의 근거(`[[thread:ID]]` · `[[task:ID]]`)는 **칩**으로 그려져 누르면 상세가 열린다.

| `get_decision_risks` | 결정 병목 리스크를 사람 · 파트로 좁혀 읽는다 | 10-2 (2026-10-15) |

## 결정 병목 리스크 (2번) — 된 것

계약 `docs/api/risk.md` · 순서 `server/PLAN.md` 10단계 · `web/PLAN.md` 11단계.

- **계산 (규칙, AI 아님)** — `GET /api/projects/{projectId}/risks`
  - 안건 신호 여덟: 기한 지남 · 기한 임박 · 여러 번 미룸 · 오래 멈춤 · 작업을 막는 중 · 작업 기한이 먼저 · 담당자 없음 · 기한 없음
  - 작업 신호 셋: 풀어도 됨(결정됐는데 막힘) · 막힌 이유 없음 · 결정이 기한보다 늦음
  - 연쇄 영향(막힌 작업 + 그 하위), 사람별 몰림. 점수 → high · medium · low
- **기준 설정** — 문턱값 다섯(기한 임박 3일 · 미룸 2번 · 멈춤 7일 · high 6점 · medium 3점)을 **프로젝트마다** 화면에서 바꾼다. 프로젝트 관리자만
- **리스크 메뉴** (`/risks`) — 안건 리스크 · 어긋난 작업 · 사람별, [내 파트 | 전체] 를 따른다
- **챗봇 도구** — "이번 주 뭐부터 정해야 해?" 에 high 부터, 왜 · 무엇이 막히나 · 다음 할 일을 근거와 함께
- **AI 요약** — 리스크 화면의 [AI 요약]. 보이는 줄만 서버가 다시 계산하고 위쪽 안건의 배경 · 이력을 모아 Claude 가 **한 줄 총평 · 먼저 정할 것 · 바로 풀 것 · 눈에 띄는 점** 으로 정리한다. 누를 때만 부르고 남기지 않는다

판정은 규칙이, 설명은 Claude 가 한다 — 점수 · 등급을 AI 가 정하지 않아 같은 데이터면 늘 같은 결과다.
