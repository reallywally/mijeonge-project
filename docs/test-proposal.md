# 기능 테스트 관리 + AI 검토 — 기획 초안 (2026-10-26)

> 아직 계약이 없다. 열린 질문(Q53 ~ Q57)을 닫은 뒤 `docs/api/test.md` 로 계약을 쓴다. 그때 이 문서와 다르면 그쪽이 맞다.

지금 innoFlow 는 **진행 중인 작업**을 중심으로 돈다. 여기에 **기능 테스트 케이스**를 같은 프로젝트 안에서 관리하고,
AI 가 테스트 제목 · 내용을 읽어 **"이런 테스트를 더 넣어 보면 어떨까"**, **"이 테스트는 확인하는 것이 없다"** 를 말해 주게 한다.

## 왜 이 앱에서인가

테스트를 평가하려면 **"무엇이 맞는 동작인가"** 라는 기준이 있어야 한다. 이 앱에는 그 기준이 이미 쌓여 있다.

- **안건의 결정** — "비밀번호는 90일마다 바꾼다" 같은 결정이 이력(`decide` · `change`)으로 남는다. 마지막 `decide` · `change` 줄이 지금의 결정이다
- **기능 작업** — 무엇을 만드는지가 작업 제목 · 본문 · 걸린 안건으로 있다

그래서 AI 가 테스트를 **허공에서 평가하지 않고**, 걸린 결정 · 기능에 비춰 "빠진 것" · "어긋난 것" 을 근거와 함께 말할 수 있다.
그리고 **결정이 바뀌면 낡은 테스트를 규칙만으로 찾을 수 있다** — 다른 테스트 도구에는 없는 이 앱만의 자리다.

## 범위

| | 다루나 | 왜 |
| --- | --- | --- |
| **앱에서 쓰는 기능 테스트 케이스** (QA 시나리오 · 통합 시나리오 · 인수 테스트) | **1차** | 제목 · 절차 · 기대 결과가 글이라 AI 가 읽을 수 있고, 결정 · 기능과 바로 이을 수 있다 |
| 코드로 된 단위 · 통합 테스트 (pytest · vitest 등) | 나중 (Q57) | 앱이 코드를 모른다. CI 결과 파일(JUnit XML)을 들여와 이름 · 결과를 읽는 연동이 따로 필요하다 |

## 흐름

1. 기능 작업 상세에서 **[테스트 추가]** — 또는 '테스트' 메뉴에서 바로 쓴다
2. 테스트에 **절차 · 기대 결과**를 적고, 확인할 **기능 작업**과 근거 **안건**을 건다
3. **[AI 테스트 검토]** — 확인하는 것이 없는 테스트 · 중복 · 나눌 것 · 결정과 어긋난 것을 이유와 함께. 사람이 고치거나 둔다
4. 기능 작업에서 **[AI 빠진 테스트 찾기]** — 정상 · 경계 · 오류 · 권한 관점에서 빠진 케이스 초안 → 사람이 골라 [추가]
5. 테스트를 돌리고 **결과(통과 · 실패 · 막힘)** 를 남긴다 — 실패면 메모
6. 걸린 안건의 결정이 바뀌면 테스트에 **'기준 바뀜'** 표시 → 사람이 고치거나 "그대로 맞다" 로 확인

## 정해 둔 것 (초안)

| | 결정 | 왜 |
| --- | --- | --- |
| 테스트는 무엇인가 | **작업에 종류를 더한다** — `Task.kind = 'work' \| 'test'`. 담당자 · 파트 · 안건 연결 · 댓글 · 확인 요청 · 회의록 출처를 그대로 쓴다 (Q55) | 새 엔티티를 세우면 위 기능을 다 다시 만들어야 한다 |
| 작업 상태의 뜻 | 테스트에서는 **케이스를 쓰는 상태**다 — 할 일(쓸 것) · 진행(쓰는 중) · 완료(돌릴 준비 됨) | 실행 결과는 상태가 아니다. 같은 테스트를 여러 번 돌린다 |
| 실행 결과 | **실행 기록 `test_run`** 한 줄씩 — 통과 · 실패 · 막힘, 누가 · 언제 · 메모. 화면은 마지막 결과를 보인다 (Q54) | 결과가 상태 칸에 섞이면 "언제 깨졌나" 를 잃는다. `task_log` 와 같은 생각 |
| 무엇을 확인하나 | **확인 대상 링크 `test_target`**(테스트 ↔ 기능 작업, 여럿 가능). 상위 작업(`parent_id`)으로 잇지 않는다 (Q56) | 테스트를 하위 작업으로 두면 진척 · 리스크 · 리포트의 '남은 하위 작업' 이 테스트 수만큼 부푼다. 테스트 하나가 기능 여럿을 지나가기도 한다 |
| 진척 · 리스크 · 리포트 | **테스트는 세지 않는다.** 작업 목록 · 간트에는 [작업 \| 테스트] 로 가른다 | 완료율이 테스트를 쓴 양으로 흔들리면 안 된다 |
| 본문 | 작업 본문 줄(`TaskLine`)에 종류 둘을 더한다 — `step`(절차) · `expect`(기대 결과). 사전조건은 `bullet` | 칸을 새로 만들지 않고 줄 편집기를 그대로 쓴다. AI 도 줄 종류로 읽는다 |
| 레벨 | `기능` · `통합` · `인수` 셋 중 하나(선택) | 분류 · 커버리지에만 쓴다. 판정에 쓰지 않는다 |
| 낡음 판정 | 테스트마다 **`basis_seq`** — 마지막으로 기준을 확인했을 때 걸린 안건들의 최대 Entry `seq`. 그 뒤에 `decide` · `change` 줄이 생기면 '기준 바뀜' | 시각이 아니라 `seq` 로 순서를 본다 (`API.md` Q15). 만들 때 · 고칠 때 · "그대로 맞다" 를 누를 때 갱신 |

## 데이터 (초안)

```
task                       -- 기존 테이블에 더한다
  kind        'work' | 'test'           (기본 'work', 기존 줄은 모두 work)
  test_level  '기능' | '통합' | '인수' | null   (test 일 때만)
  basis_seq   bigint | null              (test 일 때만)

task_line.kind             -- 'check' | 'bullet' 에 'step' | 'expect' 를 더한다

test_target                -- 테스트가 확인하는 기능 작업
  test_id, task_id, project_id          (같은 프로젝트만 — 복합 FK, task_thread_link 와 같게)

test_run
  id, project_id, test_id
  result      'pass' | 'fail' | 'blocked'
  note        text                       (실패 · 막힘이면 비우면 안 된다)
  run_by (member), run_at, seq
```

## 화면

- **기능 작업 상세** — '테스트' 칸: 걸린 테스트 한 줄씩(마지막 결과 · 기준 바뀜 표시) · [테스트 추가] · [AI 빠진 테스트 찾기]
- **테스트 상세** — 작업 상세와 같은 틀 + 절차 · 기대 결과 줄, 확인 대상 칩, **[결과 남기기]**, 실행 기록 목록, '기준 바뀜' 이면 바뀐 결정 줄과 [고치기] · [그대로 맞다]
- **'테스트' 메뉴** (`/tests`) — [내 파트 \| 전체]
  - 숫자 카드: 테스트 수 · 마지막 결과(통과 / 실패 / 막힘 / 안 돌림) · 기준 바뀜 · **테스트 없는 기능**
  - 표: 테스트 · 확인 대상 · 레벨 · 마지막 결과 · 담당
  - **[AI 테스트 검토]** — 보이는 테스트(또는 고른 것)를 검토
- **작업 목록 · 간트** — [작업 \| 테스트] 토글. 기본은 작업

## AI — 네 자리

판정은 **규칙**이, 설명 · 제안은 **AI** 가 한다 — 결정 병목 리스크 · 진행 리포트와 같은 원칙이다.
AI 는 아무것도 저장하지 않는다. 고치기 · 추가 · 지우기는 늘 사람이 누른다.

### ① [AI 테스트 검토] — "이 테스트는 의미가 없다"

**규칙이 먼저 거른다 (AI 없이)** — 기대 결과(`expect`) 줄이 없음 · 확인 대상이 없음 · 제목만 있고 본문이 없음.
이건 AI 를 부르기 전에 화면에 바로 보인다.

**AI 가 읽는 것** — 테스트 제목 · 절차 · 기대 결과, 확인 대상 기능의 제목 · 본문, 걸린 안건의 **지금 결정**, 같은 기능의 다른 테스트 제목.

**AI 가 붙이는 판정** (테스트마다 하나, 문제 없으면 안 낸다)

| 판정 | 뜻 | 예 |
| --- | --- | --- |
| `unverifiable` 확인할 기준 없음 | 기대 결과가 "잘 된다" · "정상 동작" 처럼 통과 / 실패를 가를 수 없다 | "로그인이 잘 되는지 확인" → "올바른 계정이면 대시보드로 이동하고 헤더에 이름이 보인다" 로 |
| `split` 나눌 것 | 한 테스트가 서로 다른 것을 여럿 확인한다 — 하나가 깨지면 어디인지 모른다 | 가입 · 로그인 · 비밀번호 변경을 한 테스트에서 |
| `duplicate` 중복 | 다른 테스트와 같은 것을 확인한다 | HW-41 과 HW-44 가 같은 입력 · 같은 기대 결과 |
| `conflicts` 결정과 어긋남 | 기대 결과가 걸린 안건의 지금 결정과 다르다 | 결정은 "90일" 인데 테스트는 "60일 뒤 변경 요구" |
| `trivial` 확인하는 것이 거의 없음 | 화면이 열리는지만 본다 등, 기능의 결정 · 규칙을 하나도 건드리지 않는다 | "설정 화면이 열린다" 만 있는 테스트 |

**답의 모양** (JSON 하나, 선행 관계 제안과 같은 틀)

```json
{"reviews": [{"test": "HW-41", "verdict": "conflicts",
  "reason": "걸린 안건의 지금 결정은 90일인데 기대 결과가 60일이다",
  "fix": "90일이 지난 계정으로 로그인하면 비밀번호 변경 화면으로 간다"}]}
```

서버가 받은 키를 id 로 되돌리고, 넣지 않은 키 · 이유 없는 줄은 버린다. `conflicts` 는 근거 안건 id 가 받은 데이터에 있을 때만 남긴다.

### ② [AI 빠진 테스트 찾기] — "이런 테스트를 추가해 보세요"

기능 작업 하나에서 누른다.

- **AI 가 읽는 것** — 기능 작업 제목 · 본문 · 하위 작업, 걸린 안건의 지금 결정 · 후보 · 이력, 이미 있는 테스트(제목 · 기대 결과)
- **관점** — 정상 · 경계값 · 오류 입력 · 권한(다른 사람 · 다른 프로젝트) · 동시에 두 번 · 결정이 바뀐 자리(회귀)
- **답** — 케이스마다 제목 · 관점 · 절차 · 기대 결과 · **근거**(`[[thread:ID]]` · `[[task:ID]]`). 이미 있는 테스트와 겹치는 것은 내지 않는다. 최대 8개
- **등록** — 사람이 고르고 고쳐 [추가]. 챗봇의 **작업 초안(`propose_tasks`) → `POST .../tasks/batch`(한 트랜잭션)** 을 그대로 쓰고, `kind='test'` · 확인 대상 링크만 더한다

### ③ 기준 바뀜 — 결정이 바뀐 뒤의 낡은 테스트

- **찾는 것은 규칙이다** — 걸린 안건(테스트에 직접 걸린 것 + 확인 대상 기능에 걸린 것)에 `basis_seq` 뒤로 `decide` · `change` 줄이 생겼나
- **AI 는 설명만** — 테스트 상세의 '기준 바뀜' 칸에서 [어디가 바뀌었나] 를 누르면 바뀌기 전 · 뒤 결정과 테스트를 같이 읽고 "기대 결과 둘째 줄이 옛 결정(60일) 기준이다 → 90일로" 처럼 고칠 자리를 짚는다

### ④ 챗봇 도구 · 커버리지

- 도구 `get_test_coverage(task_id?, part_id?)` — 기능별 테스트 수 · 마지막 결과 · 기준 바뀜 · 테스트 없는 기능을 읽는다
- "로그인 쪽 테스트 빠진 거 있어?" · "이번 주 깨진 테스트 뭐야?" · "결정 바뀌어서 고쳐야 할 테스트 있어?" 에 근거 칩과 함께 답한다
- 진행 리포트에 '테스트' 한 단락을 더하는 것은 나중 — 실행 기록이 몇 주 쌓인 뒤

## 요청 (초안)

| | 경로 | 비고 |
| --- | --- | --- |
| 테스트 쓰기 | 기존 작업 API 에 `kind` · `testLevel` 을 더한다 | 목록은 `?kind=test` |
| 확인 대상 | `PUT · DELETE /api/tasks/{testId}/targets/{taskId}` | 멱등. 같은 프로젝트 · 대상은 `kind='work'` 만 |
| 결과 남기기 | `POST /api/tasks/{testId}/runs` `{ result, note }` | 실행 기록 목록은 `GET` |
| 기준 확인 | `POST /api/tasks/{testId}/basis` | "그대로 맞다" — `basis_seq` 를 지금으로 |
| 커버리지 | `GET /api/projects/{projectId}/tests/coverage` | 규칙만. 숫자 카드 · 표 · 테스트 없는 기능 |
| AI 검토 | `POST /api/projects/{projectId}/tests/review` `{ testIds? }` | 한 번 · JSON · 저장 안 함. 챗봇과 같은 제한기(분당) |
| AI 빠진 테스트 | `POST /api/tasks/{taskId}/tests/suggest` | 한 번 · JSON · 저장 안 함. [추가] 는 `POST .../tasks/batch` |
| AI 바뀐 자리 | `POST /api/tasks/{testId}/basis/explain` | 한 번 · SSE · 저장 안 함 |

AI 셋은 [AI 선행 관계 찾기] · 리스크 [AI 요약] 과 같은 틀이다 — 키가 없으면 503 `CHAT_UNAVAILABLE`, 분당 제한 429, 넣어 준 id 만 근거로 남긴다.

## 조심할 것

- **AI 판정은 제안이다.** '의미 없음' 을 받아도 테스트를 지우거나 숨기지 않는다. 사람이 "그대로 둔다" 를 고를 수 있다
- **사람이 아니라 테스트를 본다.** "누가 테스트를 못 썼나" 가 아니라 "어느 기능이 덜 확인됐나" 로 말한다
- **결정이 없는 기능**에는 `conflicts` 를 내지 않는다 — 기준이 없으면 어긋날 수도 없다. 대신 "결정이 없어 기대 결과를 확인할 기준이 없다" 를 한 번만 알린다
- **지어낸 근거 금지** — 근거 칩은 넣어 준 안건 · 작업 id 로만 (챗봇 · 리포트와 같은 규칙)

## 안 하는 것

- 테스트 자동 실행 · 브라우저 자동화 · 코드 생성
- AI 가 테스트를 바로 저장 · 고치기 · 지우기
- 결과를 사람 점수로 쓰기

## 순서

1. **데이터 · API · 화면 (AI 없이)** — `kind` · `step` / `expect` 줄 · `test_target` · `test_run` · `basis_seq`, 테스트 메뉴 · 커버리지(규칙) · '기준 바뀜' 표시. 진척 · 리스크 · 리포트에서 테스트 빼기. **`test_run` 과 `basis_seq` 는 처음부터** — 늦게 넣으면 그 앞 기록 · 기준은 되살릴 수 없다
2. **② [AI 빠진 테스트 찾기]** — 작업 초안 · 일괄 등록을 재사용해 가장 빨리 쓸모가 보인다
3. **① [AI 테스트 검토]** — 규칙 거르기 + AI 판정 다섯
4. **③ 바뀐 자리 설명 · ④ 챗봇 도구**
5. 나중 — CI 결과(JUnit XML) 들여오기 (Q57), 리포트의 테스트 단락
6. 평가 — 시드에 일부러 나쁜 테스트(기준 없음 · 중복 · 어긋남)를 섞어 두고 AI 가 잡는지 센다. 7-3 평가셋 옆에 둔다

## 열린 질문

- **Q53 · 누가 테스트를 쓰나** — 개발자 · QA · 기획자 중 누가 주로 쓰고 돌리나. 화면 말("케이스" · "시나리오") · 레벨 이름 · 기본 보기가 갈린다
- **Q54 · 같은 테스트를 여러 번 돌리나** — 릴리스 · 스프린트마다 다시 돌리면 실행 기록이 꼭 필요하다(초안은 '그렇다' 로 1차에 넣음). 한 번만 돌린다면 실행 기록 대신 결과 칸 하나로 줄일 수 있다
- **Q55 · 테스트를 작업으로 둘까, 따로 둘까** — 초안은 작업 + `kind`. 테스트에만 필요한 것(실행 묶음 · 환경 · 버전)이 많아지면 별도 엔티티가 낫다
- **Q56 · 기능과 잇는 방법** — 초안은 별도 링크(`test_target`). 상위 작업으로 잇는 쪽이 쉽지만 진척 숫자가 흔들린다
- **Q57 · 코드 테스트(단위 · 통합) 결과를 들여올까** — CI 의 JUnit XML 을 받아 테스트 이름 · 결과를 붙이는 연동. 들여오면 AI 가 "기능 케이스는 있는데 자동화가 없는 자리" 도 말할 수 있다
