# 기능 테스트 관리 + AI 검토 — 기획 초안 (2026-10-26)

> 아직 계약이 없다. 열린 질문은 모두 닫혔다(2026-10-27) — 다음은 `docs/api/test.md` 로 계약을 쓰는 일이다. 그때 이 문서와 다르면 그쪽이 맞다.
>
> **2026-10-26 사용자 결정** — 테스트를 **작업에서 떼어 따로 둔다.** 작업 상세에 테스트를 매달면 작업에 너무 기대어
> 여러 기능을 가로지르는 시나리오 테스트에 맞지 않는다. 상세 입력 항목도 달라 **화면도 따로** 둔다.
> 작업 · 안건은 테스트에 **참조 태그**로 건다(없어도 된다). 자유 라벨은 나중이고, 묶음은 **상위 테스트**로 한다(하위 작업처럼) —
> 작업 메뉴의 **간트차트를 그대로 써서** 묶음을 계층 트리로 본다.
> 단계는 **행동 ↔ 기대 결과를 짝**으로 적는다. — Q55 · Q56 닫힘
>
> **2026-10-27 사용자 결정** — 개발자 · 기획자 등 **누구나** 쓴다(Q53). 같은 테스트를 **반복해서 돌리지 않는다**(Q54) —
> 실행 기록 없이 결과를 테스트에 바로 둔다. 코드 테스트 결과는 **들여오지 않는다**(Q57). 간트 막대는 **테스트 기간**이다(Q58).
> **테스트 메뉴의 핵심은 지금의 상황 파악이다** — 작업 메뉴처럼 *지금 무엇을 테스트하고 있나*, *무엇이 오래 걸리나* 를 본다.
> 지난 결과의 이력(이번 주 실패했던 것 등)은 중요하지 않다.

지금 innoFlow 는 **진행 중인 작업**을 중심으로 돈다. 여기에 **기능 · 시나리오 테스트**를 같은 프로젝트 안에서 관리하고,
AI 가 테스트 제목 · 단계를 읽어 **"이런 테스트를 더 넣어 보면 어떨까"**, **"이 테스트는 확인하는 것이 없다"** 를 말해 주게 한다.

## 왜 이 앱에서인가

테스트를 평가하려면 **"무엇이 맞는 동작인가"** 라는 기준이 있어야 한다. 이 앱에는 그 기준이 이미 쌓여 있다.

- **안건의 결정** — "비밀번호는 90일마다 바꾼다" 같은 결정이 이력(`decide` · `change`)으로 남는다. 마지막 `decide` · `change` 줄이 지금의 결정이다
- **작업** — 무엇을 만드는지가 작업 제목 · 본문 · 걸린 안건으로 있다

테스트에 작업 · 안건을 태그로 걸어 두면 AI 가 테스트를 **허공에서 평가하지 않고**, 그 결정 · 기능에 비춰 "빠진 것" · "어긋난 것" 을 근거와 함께 말한다.
그리고 **결정이 바뀌면 낡은 테스트를 규칙만으로 찾을 수 있다** — 다른 테스트 도구에는 없는 이 앱만의 자리다.

## 범위

| | 다루나 | 왜 |
| --- | --- | --- |
| **앱에서 쓰는 기능 · 시나리오 테스트** (QA 시나리오 · 통합 시나리오 · 인수 테스트) | **다룬다** | 제목 · 단계 · 기대 결과가 글이라 AI 가 읽을 수 있고, 결정 · 작업과 태그로 이을 수 있다 |
| 코드로 된 단위 · 통합 테스트 (pytest · vitest 등) | **다루지 않는다** (Q57) | 앱이 코드를 모른다. CI 결과를 들여오는 연동은 하지 않는다 |

## 쓰는 사람

**그 프로젝트 멤버 누구나** — 개발자 · 기획자 · QA 를 가르지 않는다(Q53). 쓰기 · 고치기 · 결과 남기기 모두 같다.
지우기만 좁다 — 만든 사람 · 프로젝트 관리자 · 시스템 관리자(회의록 · 리포트와 같은 경계).
화면 말은 누구나 알아듣게 **'테스트'** 하나로 쓴다 — '케이스' · '시나리오' 를 섞지 않는다.

## 흐름

1. **'테스트' 메뉴**에서 [테스트 추가] — 또는 작업 · 안건 상세의 [테스트 추가] (그 작업 · 안건이 태그로 미리 걸린 채 열린다)
2. **단계를 행동 ↔ 기대 결과 짝으로** 적고, 필요하면 **작업 · 안건을 태그로** 건다. 여러 테스트는 **상위 테스트** 아래로 묶고, **테스트 기간**을 잡는다
3. **[AI 테스트 검토]** — 확인하는 것이 없는 테스트 · 중복 · 나눌 것 · 결정과 어긋난 것을 이유와 함께. 사람이 고치거나 둔다
4. **[AI 빠진 테스트 찾기]** — 작업 · 안건 또는 테스트 묶음을 골라, 빠진 케이스 초안 → 사람이 골라 [추가]
5. 다 쓰면 **준비됨**, 돌리기 시작하면 **테스트 중**, 끝나면 **통과 · 실패 · 막힘** — 실패면 몇 번째 단계인지와 메모
6. 테스트 메뉴에서 **지금 테스트 중인 것 · 오래 걸리는 것 · 기간이 지난 것**을 본다 — 상태마다 "N일째" 가 붙는다
7. 태그한 안건의 결정이 바뀌면 테스트에 **'기준 바뀜'** 표시 → 사람이 고치거나 "그대로 맞다" 로 확인

## 정해 둔 것 (초안)

| | 결정 | 왜 |
| --- | --- | --- |
| 테스트는 무엇인가 | **작업과 따로 둔다** — 테이블 `test_case`, 화면 · API 도 따로 (Q55 닫힘) | 입력 항목이 다르고, 시나리오는 여러 기능을 가로지른다. 진척 · 리스크 · 리포트 · 작업 간트에 **처음부터 섞이지 않는다** — 테스트를 일일이 빼는 처리가 필요 없다 |
| 작업 · 안건과의 관계 | **참조 태그** `test_ref` — 테스트 하나에 작업 · 안건을 0개 이상. 필수가 아니다 (Q56 닫힘) | 작업이 끝나거나 지워져도 테스트는 그대로다. 한 테스트가 여러 기능을 지나가기도 한다 |
| 태그 종류 | **작업 · 안건 참조만.** 자유 라벨(`로그인` · `결제`)은 나중 | 묶어 보기는 상위 테스트가 맡는다. 라벨은 쓰임이 보이면 더한다 |
| 묶음 | **상위 테스트** `parent_id` — 하위 작업과 같은 방식. 자기 · 자손을 부모로 두면 고리라 서버가 막는다 | "결제 시나리오" 아래 정상 결제 · 카드 거절 · 취소 처럼. 간트가 계층 트리로, 목록이 작업과 같은 경로 표시로 보인다 |
| 묶음의 상태 | 하위가 있는 테스트는 **직접 돌리지 않는다** — 하위 상태를 모아 보인다(가장 나쁜 것: 실패 > 막힘 > 테스트 중 > 작성 중 · 준비됨 > 통과) | 묶음 줄만 보고도 어디가 깨졌는지 안다 |
| 단계 | **행동 ↔ 기대 결과 짝** `test_step` 의 순서 있는 줄. 중간 단계는 기대 결과를 비울 수 있지만, **기대 결과가 하나도 없는 테스트는 '확인할 것 없음'** 이다 | 시나리오는 단계마다 확인할 것이 있다. 실패를 "몇 번째 단계" 로 짚을 수 있다 |
| 상태 | **칸 하나** — 작성 중 → 준비됨 → **테스트 중** → **통과 · 실패 · 막힘**. 실패를 고친 뒤 다시 돌리면 테스트 중으로 되돌린다 | 반복해서 돌리지 않는다(Q54) — 한 방향으로 흐르니 작업 상태처럼 칸 하나면 된다. '테스트 중' 이 있어야 지금 무엇을 테스트하는지 보인다 |
| 며칠째 | **`status_changed_at`** — 상태가 바뀐 때 하나. 서버가 찍는다. 화면은 "테스트 중 · 5일째" · "막힘 · 8일째" | 상황 파악의 바탕이다. 이력은 두지 않는다 — 마지막으로 바뀐 때만 있으면 지금이 보인다(작업의 `statusChangedAt` 과 같은 자리) |
| 손쓸 테스트 신호 | **규칙으로** 붙인다 (아래 '신호'). 문턱값은 **리스크 기준(`RiskSettings`) 그대로** | 진행 리포트가 리스크 기준을 그대로 쓰는 것과 같은 이유 — 기준이 두 벌이면 화면마다 다른 말을 한다 |
| 결과 | 상태를 바꿀 때 **누가 · 언제**를 서버가 찍는다(`status_changed_by` · `status_changed_at`). 실패 · 막힘은 **메모**(필수)와 실패한 단계 번호(선택). 고친 뒤 다시 돌리면 **덮어쓴다** — 이력은 남기지 않는다 | 실행 기록 테이블을 두지 않는다. 이력이 필요해지면 그때 `task_log` 같은 기록을 더한다 |
| 테스트 기간 | **`start` · `due`**(선택) — 이 테스트를 언제 돌리나 (Q58). 둘 다 비우면 간트에 '기간 미정' 으로 서고 막대가 없다(작업과 같다) | "통합 테스트 주간" 처럼 돌릴 때를 잡는다. 기한이 지났는데 아직 안 돌린 것을 규칙으로 센다 |
| 그 밖의 칸 | 목적(한두 줄) · 사전조건 · 테스트 데이터 · 레벨(`기능` · `통합` · `인수`, 선택) · 담당자 · 파트 | 담당자 · 파트는 작업과 같은 뜻 · 같은 거르기(내 파트 · 전체). 댓글 · 확인 요청은 없다 |
| 번호 | 프로젝트 접두사 + `T` + 순번 — `HW-T12` | 작업 번호(`HW-12`)와 헷갈리지 않고, 챗봇의 @ 언급 · 칩으로 가리킬 수 있다 |
| 낡음 판정 | 테스트마다 **`basis_seq`** — 마지막으로 기준을 확인했을 때 **닿는 안건**들의 최대 Entry `seq`. 그 뒤에 `decide` · `change` 줄이 생기면 '기준 바뀜'. 닿는 안건 = 직접 태그한 안건 + 태그한 작업에 걸린 안건 | 시각이 아니라 `seq` 로 순서를 본다 (`API.md` Q15). 만들 때 · 고칠 때 · 태그를 바꿀 때 · "그대로 맞다" 를 누를 때 갱신. **처음부터 넣는다** — 늦게 넣으면 그 앞 기준은 되살릴 수 없다 |

## 신호 — 손쓸 테스트 (규칙, AI 없이)

작업의 '손쓸 작업' 신호(`docs/api/report.md`)와 같은 셈법이다. 날 수는 한국 시간 날짜로 센다. 하위가 있는 묶음에는 붙이지 않는다.

| 신호 | 규칙 | 화면 말 |
| --- | --- | --- |
| `longRunning` | **테스트 중**인 날 수가 테스트 기간(`start` ~ `due`)의 1.5배를 넘음. 기간이 없으면 `staleDays` 를 넘음 | 오래 걸림 |
| `overdue` | `due` 가 지났는데 통과가 아님 | 기간 지남 |
| `notStarted` | `start` 가 지났는데 아직 작성 중 · 준비됨 | 시작 안 함 |
| `longBlocked` | **막힘**인 날 수가 `staleDays` 를 넘음 | 오래 막힘 |
| `failedIdle` | **실패**인 날 수가 `staleDays` 를 넘음 — 고쳐서 다시 돌리지 않고 있다 | 실패 그대로 |
| `basisChanged` | 닿는 안건의 결정이 바뀜 (아래 '낡음 판정') | 기준 바뀜 |

신호가 붙은 테스트를 **손쓸 테스트**로 모아 기간 지남 · 오래 막힘 · 오래 걸림 순으로, 같으면 날 수가 긴 것부터 보인다.

## 데이터 (초안)

```
test_case
  id, project_id, key ('HW-T12'), seq
  title, purpose, precondition, test_data       (글. purpose · precondition · test_data 는 비워도 된다)
  parent_id | null                              (같은 프로젝트의 test_case — 복합 FK, 고리는 서버가 막는다)
  status      'draft' | 'ready' | 'testing' | 'pass' | 'fail' | 'blocked'
  status_changed_at, status_changed_by (member) (상태가 바뀔 때 서버가 찍는다 — "N일째" · 누가의 바탕)
  failed_step int | null                        (fail 일 때 몇 번째 단계였나, 선택)
  result_note text | null                       (fail · blocked 면 비우면 안 된다)
  level       '기능' | '통합' | '인수' | null
  start, due  date | null                       (테스트 기간 — 작업과 같이 둘 다 · 하나만 · 없음 허용)
  owner_id (member) | null, part_id | null
  basis_seq   bigint | null
  created_by (member), created_at

test_step                                       -- 행동 ↔ 기대 결과 짝, 순서대로
  id, test_id, sort_order
  action      text                              (비우면 안 된다)
  expected    text                              (비울 수 있다)

test_ref                                        -- 참조 태그
  test_id, project_id
  task_id | thread_id                           (둘 중 정확히 하나 — check_request 와 같게, 같은 프로젝트만)
```

## 화면

- **'테스트' 메뉴** (`/tests`) — 작업 메뉴와 같은 틀. 보기 둘 **[목록 \| 간트]**, [내 파트 \| 전체], 제목 · 담당자 거르기
  - **맨 위는 '지금'** — 작업 메뉴의 '눈여겨볼 것' 자리
    - 숫자 카드: **테스트 중** · 오래 걸림 · 기간 지남 · 막힘 · 실패 · 기준 바뀜. 누르면 그 테스트만 거른다
    - **지금 테스트 중** — 테스트 · 담당 · "N일째" · 테스트 기간(남은 날 / 지난 날)
    - **손쓸 테스트** — 신호가 붙은 테스트 · 신호 칩 · 담당 · N일째
  - 아래 전체 숫자는 작게: 테스트 수 · 상태별 · 태그 없는 테스트
  - **목록** — 테스트 · 경로(상위 테스트) · 태그 칩 · 레벨 · **상태 · N일째** · 신호 칩 · 테스트 기간 · 담당
  - **간트** — 작업 간트(`TaskGantt`)를 그대로 쓴다. 왼쪽은 **묶음 계층 트리**(번호 · 제목 · 상태 배지), 오른쪽 막대는 **테스트 기간**(기간 지남 · 오래 걸림은 작업 간트와 같은 색). 막대를 끌어 기간을 바꾸고, 줄의 [+] 로 그 묶음 아래에 테스트를 더한다. 묶음 줄은 하위 상태를 모아 보인다. 선행 관계 화살표는 없다
  - **[AI 테스트 검토]** · **[AI 빠진 테스트 찾기]**
- **테스트 상세** — 작업 상세와 **따로 만든 팝업**(주소 `/tests/:id`)
  - 위: 번호 · 제목 · 상태 · 레벨 · 담당자 · 파트 · 상위 테스트 · 테스트 기간
  - **태그** — 작업 번호 · 안건 제목으로 찾아 거는 칩(상위 작업 찾기와 같은 방식). 누르면 그 작업 · 안건 상세
  - 목적 · 사전조건 · 테스트 데이터
  - **단계 표** — `#` · 행동 · 기대 결과. 줄 추가 · 순서 끌기 · 지우기
  - **상태 바꾸기** — [테스트 시작] → [통과] · [실패] · [막힘]. 실패 · 막힘은 메모 · 실패한 단계를 받는다. 지금 상태 · N일째 · 누가 바꿨는지를 보이고, 다시 돌리면 덮어쓴다
  - '기준 바뀜' 이면 바뀐 결정 줄 · [어디가 바뀌었나] · [고치기] · [그대로 맞다]
- **작업 상세 · 안건 상세** — '이 작업(안건)을 태그한 테스트' 를 **읽기 전용 칩**으로(상태 색), [테스트 추가](태그가 걸린 채 열린다). 테스트를 여기서 편집하지 않는다

## AI — 네 자리

판정은 **규칙**이, 설명 · 제안은 **AI** 가 한다 — 결정 병목 리스크 · 진행 리포트와 같은 원칙이다.
AI 는 아무것도 저장하지 않는다. 고치기 · 추가 · 지우기는 늘 사람이 누른다.

**태그가 AI 의 기준을 정한다.** 태그가 없는 테스트도 글만으로 검토하지만(기준 없음 · 나눌 것 · 중복 · 확인할 것 거의 없음),
'결정과 어긋남' 과 '기준 바뀜' 은 **안건에 닿는 테스트만** 받는다.

### ① [AI 테스트 검토] — "이 테스트는 의미가 없다"

**규칙이 먼저 거른다 (AI 없이)** — 단계가 없음 · 기대 결과가 하나도 없음 · 제목만 있음. 화면에 바로 보이고 AI 에 넘기지 않는다.

**AI 가 읽는 것** — 테스트 제목 · 목적 · 사전조건 · 단계(행동 ↔ 기대 결과), 태그한 작업의 제목 · 본문, **닿는 안건의 지금 결정**,
같은 묶음 · 같은 태그를 가진 다른 테스트의 제목 · 기대 결과.

**AI 가 붙이는 판정** (테스트마다 하나, 문제 없으면 안 낸다)

| 판정 | 뜻 | 예 |
| --- | --- | --- |
| `unverifiable` 확인할 기준 없음 | 기대 결과가 "잘 된다" · "정상 동작" 처럼 통과 / 실패를 가를 수 없다 | 3단계 기대 결과 "로그인이 잘 된다" → "대시보드로 이동하고 헤더에 이름이 보인다" 로 |
| `split` 나눌 것 | 한 테스트가 서로 다른 것을 여럿 확인한다 — 하나가 깨지면 어디인지 모른다. **시나리오는 예외** — 한 흐름을 따라가는 단계는 나누라 하지 않는다 | 서로 무관한 가입 · 비밀번호 변경 · 알림 설정을 한 테스트에서 |
| `duplicate` 중복 | 다른 테스트와 같은 것을 확인한다 | HW-T4 와 HW-T9 가 같은 입력 · 같은 기대 결과 |
| `conflicts` 결정과 어긋남 | 기대 결과가 닿는 안건의 지금 결정과 다르다 | 결정은 "90일" 인데 2단계 기대 결과는 "60일 뒤 변경 요구" |
| `trivial` 확인하는 것이 거의 없음 | 화면이 열리는지만 본다 등, 결정 · 규칙을 하나도 건드리지 않는다 | "설정 화면이 열린다" 만 있는 테스트 |

**답의 모양** (JSON 하나, 선행 관계 제안과 같은 틀). 고칠 자리는 단계 번호로 짚는다.

```json
{"reviews": [{"test": "HW-T4", "verdict": "conflicts", "step": 2,
  "reason": "태그한 안건의 지금 결정은 90일인데 2단계 기대 결과가 60일이다",
  "fix": "90일이 지난 계정으로 로그인하면 비밀번호 변경 화면으로 간다"}]}
```

서버가 받은 번호를 id 로 되돌리고, 넣지 않은 번호 · 없는 단계 · 이유 없는 줄은 버린다. `conflicts` 는 그 테스트가 안건에 닿을 때만 남긴다.

### ② [AI 빠진 테스트 찾기] — "이런 테스트를 추가해 보세요"

테스트 메뉴에서 **무엇을 기준으로 찾을지 고른다** — 작업 · 안건 하나, 또는 테스트 묶음(상위 테스트) 하나.
작업 · 안건 상세의 [테스트 추가] 옆에서도 그 작업 · 안건으로 바로 연다.

- **AI 가 읽는 것**
  - 작업 · 안건으로: 작업 제목 · 본문 · 하위 작업, 닿는 안건의 지금 결정 · 후보 · 이력, 그것을 태그한 테스트(제목 · 단계)
  - 묶음으로: 묶음의 목적, 하위 테스트 전부(단계까지), 하위 테스트들이 태그한 작업 · 안건
- **관점** — 정상 · 경계값 · 오류 입력 · 권한(다른 사람 · 다른 프로젝트) · 동시에 두 번 · 결정이 바뀐 자리(회귀) · 묶음이면 **빠진 분기**(카드 거절 뒤 재시도 등)
- **답** — 케이스마다 제목 · 관점 · **단계(행동 ↔ 기대 결과)** · 태그할 작업 · 안건 · **근거**(`[[thread:ID]]` · `[[task:ID]]`). 이미 있는 테스트와 겹치는 것은 내지 않는다. 최대 8개
- **등록** — 사람이 고르고 고쳐 [추가] → `POST .../tests/batch`(한 트랜잭션). 작업 초안 → 일괄 등록과 같은 흐름이고, 태그 · 상위 테스트가 미리 채워진다. 새 테스트는 **작성 중**으로 들어간다

### ③ 기준 바뀜 — 결정이 바뀐 뒤의 낡은 테스트

- **찾는 것은 규칙이다** — 닿는 안건에 `basis_seq` 뒤로 `decide` · `change` 줄이 생겼나
- **이미 통과한 테스트도 표시한다** — 옛 결정으로 통과한 것이라 다시 볼 일이다. 고치면 상태를 준비됨으로 되돌릴지 사람이 고른다
- **AI 는 설명만** — 테스트 상세의 [어디가 바뀌었나] 를 누르면 바뀌기 전 · 뒤 결정과 단계를 같이 읽고 "2단계 기대 결과가 옛 결정(60일) 기준이다 → 90일로" 처럼 고칠 단계를 짚는다

### ④ 챗봇 도구

- 도구 `get_tests(task_id?, thread_id?, part_id?, status?, signal?)` — 테스트 · 상태 · N일째 · 신호 · 태그 · 테스트 기간을 읽는다
- 도구 `get_test(test_id)` — 단계 · 결과 메모까지
- **"지금 테스트 중인 거 뭐야?" · "오래 걸리는 테스트 있어?"** · "기간 지났는데 안 끝난 테스트" · "로그인 쪽 테스트 빠진 거 있어?" · "결정 바뀌어서 고쳐야 할 테스트 있어?" 에 근거 칩과 함께 답한다. 칩에 테스트(`[[test:ID]]`)를 더한다
- 진행 리포트에 '테스트' 한 단락(지금 테스트 중 · 손쓸 테스트)을 더하는 것은 나중

## 요청 (초안)

| | 경로 | 비고 |
| --- | --- | --- |
| 목록 · 추가 | `GET · POST /api/projects/{projectId}/tests` | 목록은 상태 · `statusChangedAt` · 신호 · 태그 · 테스트 기간까지 — '지금' · 목록 · 간트가 같이 쓴다. 신호는 서버가 계산한다 |
| 읽기 · 고치기 · 지우기 | `GET · PATCH · DELETE /api/tests/{testId}` | 단계는 `PATCH` 에 **목록째** 싣는다(순서 · 짝을 한 번에). 하위가 있으면 지우기 409. 지우기는 만든 사람 · 관리자 |
| 상태 | `POST /api/tests/{testId}/status` `{ status, failedStep?, note? }` | 다섯 상태 어디로든. `status_changed_at` · 누가는 서버가 찍고, 다시 부르면 덮어쓴다. 실패 · 막힘은 메모 필수. 하위가 있는 테스트는 400 |
| 태그 | `PUT · DELETE /api/tests/{testId}/refs/{kind}/{id}` | `kind` = `task` \| `thread`. 멱등 · 같은 프로젝트만 |
| 기준 확인 | `POST /api/tests/{testId}/basis` | "그대로 맞다" — `basis_seq` 를 지금으로 |
| 태그한 테스트 | `GET /api/tasks/{taskId}/tests` · `GET /api/threads/{threadId}/tests` | 작업 · 안건 상세의 읽기 전용 칩 |
| 일괄 추가 | `POST /api/projects/{projectId}/tests/batch` | AI 초안 [추가]. 한 트랜잭션 |
| AI 검토 | `POST /api/projects/{projectId}/tests/review` `{ testIds? }` | 한 번 · JSON · 저장 안 함. 챗봇과 같은 제한기(분당) |
| AI 빠진 테스트 | `POST /api/projects/{projectId}/tests/suggest` `{ taskId \| threadId \| testId }` | 한 번 · JSON · 저장 안 함 |
| AI 바뀐 자리 | `POST /api/tests/{testId}/basis/explain` | 한 번 · SSE · 저장 안 함 |

AI 셋은 [AI 선행 관계 찾기] · 리스크 [AI 요약] 과 같은 틀이다 — 키가 없으면 503 `CHAT_UNAVAILABLE`, 분당 제한 429, 넣어 준 id 만 근거로 남긴다.
경로의 `testId` 는 `require_scope` 의 경계 검사에 더한다(없거나 남의 프로젝트면 404 `TEST_NOT_FOUND`).

## 조심할 것

- **AI 판정은 제안이다.** '의미 없음' 을 받아도 테스트를 지우거나 숨기지 않는다. 사람이 "그대로 둔다" 를 고를 수 있다
- **사람이 아니라 테스트를 본다.** "누가 테스트를 못 썼나" 가 아니라 "어디가 덜 확인됐나" 로 말한다. 누구나 쓰는 만큼 쓴 사람을 탓하는 말투가 더 위험하다
- **안건에 닿지 않는 테스트**에는 `conflicts` 를 내지 않는다 — 기준이 없으면 어긋날 수도 없다. 대신 "태그한 결정이 없어 기대 결과를 비춰 볼 기준이 없다" 를 한 번만 알린다
- **시나리오를 쪼개라고 하지 않는다** — 한 흐름을 따라가는 여러 단계는 `split` 이 아니다
- **지어낸 근거 금지** — 근거 칩은 넣어 준 안건 · 작업 · 테스트 id 로만 (챗봇 · 리포트와 같은 규칙)

## 안 하는 것

- 테스트 자동 실행 · 브라우저 자동화 · 코드 생성
- 코드 테스트(단위 · 통합) 결과 들여오기 · CI 연동 (Q57)
- 같은 테스트의 반복 실행 · 실행 기록 · 실행 묶음(릴리스 회차) (Q54)
- AI 가 테스트를 바로 저장 · 고치기 · 지우기
- 결과를 사람 점수로 쓰기
- 자유 라벨 · 테스트 댓글 · 테스트 확인 요청 (나중에 쓰임이 보이면)

## 순서

1. **데이터 · API · 화면 (AI 없이)** — `test_case` · `test_step` · `test_ref` · `status_changed_at` · `basis_seq`, **신호(규칙) · 테스트 메뉴의 '지금'**(테스트 중 · 손쓸 테스트) · 목록 · 간트 · 테스트 상세 · 작업 · 안건 상세의 읽기 전용 칩. 이것만으로 테스트 메뉴의 핵심(상황 파악)이 선다
2. **② [AI 빠진 테스트 찾기]** — 초안 → 일괄 추가로 가장 빨리 쓸모가 보인다
3. **① [AI 테스트 검토]** — 규칙 거르기 + AI 판정 다섯
4. **③ 바뀐 자리 설명 · ④ 챗봇 도구**
5. 나중 — 자유 라벨, 리포트의 테스트 단락
6. 평가 — 시드에 일부러 나쁜 테스트(기준 없음 · 중복 · 어긋남 · 쪼개면 안 되는 시나리오)를 섞어 두고 AI 가 잡는지 · 잘못 잡지 않는지 센다. 7-3 평가셋 옆에 둔다

## 정한 것

- **Q53 · 누가 테스트를 쓰나** (2026-10-27) — **그 프로젝트 멤버 누구나.** 개발자 · 기획자 · QA 를 가르지 않는다. 지우기만 만든 사람 · 관리자
- **Q54 · 같은 테스트를 여러 번 돌리나** (2026-10-27) — **반복하지 않는다.** 결과는 테스트에 바로 두고 다시 돌리면 덮어쓴다. 실행 기록 테이블은 두지 않는다 — 지난 결과의 이력보다 **지금의 상황**(테스트 중 · 오래 걸림)이 중요하다. 그 바탕은 `status_changed_at` 하나다
- **Q55 · 테스트를 작업으로 둘까, 따로 둘까** (2026-10-26) — **따로.** 테이블 · 화면 · API 모두 따로. 작업에 기대면 시나리오 테스트에 맞지 않고 입력 항목도 다르다
- **Q56 · 작업과 잇는 방법** (2026-10-26) — **참조 태그**(작업 · 안건, 0개 이상). 상위 작업 · 확인 대상 링크로 매달지 않는다. 자유 라벨은 나중, 묶음은 상위 테스트
- **Q57 · 코드 테스트 결과를 들여올까** (2026-10-27) — **들여오지 않는다.** 앱에서 쓰는 기능 · 시나리오 테스트만 다룬다
- **Q58 · 간트 막대의 뜻** (2026-10-27) — **테스트 기간**(`start` · `due`, 선택). 비우면 '기간 미정'
