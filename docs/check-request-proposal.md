# 확인 요청 — 기획 초안 (2026-10-16)

> 1차 계약은 `docs/api/check.md`(합의 2026-10-16) 다. 이 문서와 다르면 그쪽이 맞다.

> 2026-10-16 사용자 결정 — **쪽지가 아니다.** 회사엔 메신저가 따로 있어 쪽지를 두면 기능이 흩어진다.
> 작업 · 안건에 붙는 **'확인해 주세요' 버튼 하나**와, 그 기록으로 관리자가 **놓치는 원인**을 보는 것까지만 한다.
>
> 2026-10-16 사용자 결정 — Q38 · Q39 · Q41 은 초안대로, Q40 은 **시간이 지나도 따로 처리하지 않는다**(놓침 기준 일수 없음). 넷 다 닫힘.

## 흐름

1. 작업 · 안건 상세에서 **[확인 요청]**
2. 사람을 고르고 **30자 미만**으로 적어 보낸다
3. 받은 사람은 **확인 요청 목록**에서 보고 **[확인]**
4. 보낸 사람은 **보낸 목록**에서 확인했는지 본다
5. (AX) 관리자가 **확인율이 낮은 원인**을 본다 — 일이 많고 어려워서 놓치나, 그냥 놓치나

## 정해 둔 것 (초안)

| | 결정 | 왜 |
| --- | --- | --- |
| 붙는 곳 | **작업이나 안건 하나에 꼭 붙는다.** 홀로 보내는 요청은 없다 | 맥락 없는 요청은 메신저의 일이다. 붙어 있어야 분석에서 '어떤 일이었나' 를 본다 |
| 받는 사람 | 여럿 고를 수 있지만 **한 사람당 한 건**으로 저장한다 | 상태가 사람마다 하나뿐이라 줄 하나가 곧 '보냄 → 확인' 이다. 확인율을 세기도 쉽다 |
| 내용 | 30자 미만(29자까지), 비우면 안 된다 | 길게 쓸 일은 메신저 · 작업 댓글 · 안건 이력이 맡는다 |
| 상태 | **둘뿐** — 대기 · 확인. 확인한 시각을 남긴다. **시간이 지나도 상태가 바뀌지 않는다** | 읽음 · 답 · 기한 · 다시 알리기 · 닫기 · '놓침' 판정을 두지 않는다 (Q40) |
| 수정 · 삭제 | 없다 | 기록이 확인율의 바탕이다 |
| 알림 | 헤더에 **대기 수 배지** 하나 (Q38) | 메신저를 대신하지 않되, 들어왔을 때 쌓인 게 보이기는 해야 한다 |
| 범위 | 그 프로젝트 멤버에게만. 자기 자신은 빼고 | 권한 경계(`docs/api/auth.md`)를 그대로 쓴다 |
| 걸린 것이 끝나면 | 작업이 '완료' 되거나 안건이 '결정' 돼도 **대기 요청은 그대로 둔다** — 확인 안 한 것으로 센다 (Q41) | 일이 끝났다고 확인한 것은 아니다 |

## 데이터

```
check_request
  id, project_id,
  task_id | thread_id               -- 둘 중 정확히 하나 (같은 프로젝트 것만, 복합 FK)
  sender_id, recipient_id (member)
  text  (1 ~ 29자)
  created_at, confirmed_at | null, seq
  -- 보낼 때의 받는 사람 부하 (분석용, 아래 'AX')
  load_open_tasks, load_blocked_tasks, load_due_soon_tasks, load_open_threads
```

**보낼 때 부하를 같이 찍는다.** 작업 상태 이력(`task_log`)이 없어 나중에는 "그때 얼마나 바빴나" 를 되살릴 수 없다.
네 숫자는 보내는 순간 받는 사람이 맡은 진행 중 · 막힘 · 기한 임박(3일) 작업 수와 안 정해진 안건 수다.

## 화면

- **작업 · 안건 상세** — [확인 요청] 버튼. 아래에 그 작업 · 안건에 걸린 요청이 한 줄씩(받는 사람 · 내용 · 확인 여부)
- **'확인 요청' 메뉴** (`/checks`) — 탭 [받은 것 | 보낸 것]
  - 받은 것: 대기 먼저, 오래된 순. 줄마다 작업 · 안건 칩(누르면 상세) · 보낸 사람 · 내용 · [확인]
  - 보낸 것: 받는 사람 · 내용 · 대기 / 확인(시각)
- **헤더 배지** — 내 대기 수

## 요청 (초안)

| | 경로 | 비고 |
| --- | --- | --- |
| 보내기 | `POST /api/projects/{projectId}/checks` `{ taskId \| threadId, recipientIds[], text }` | 받는 사람 수만큼 줄이 생긴다 |
| 목록 | `GET /api/projects/{projectId}/checks?box=inbox\|sent` | 내 것만 |
| 대기 수 | `GET /api/checks/pending-count` | 배지용. 프로젝트별 수도 같이 |
| 확인 | `POST /api/checks/{id}/confirm` | 받은 사람만. 이미 확인했으면 그대로 |
| 분석 | `GET /api/projects/{projectId}/checks/stats?from=&to=` | 프로젝트 관리자는 전부, 그 밖의 멤버는 자기 줄만 (Q39) |

## AX — 확인율이 낮은 이유

판정은 **규칙**이, 설명은 **Claude** 가 한다 — 결정 병목 리스크와 같은 원칙이다. 같은 데이터면 늘 같은 결과여야 사람에 대한 판단을 믿는다.

### 규칙이 세는 것 (Claude 없이)

사람마다, 기간 안에서:

- 받은 수 · 확인 수 · **확인율** · 확인까지 걸린 시간(중앙값)
- **안 한 것** — 지금 대기인 것. 며칠 지났는지로 따로 가르지 않는다 (Q40)
- 안 한 요청과 확인한 요청의 **보낼 때 부하** 비교 — 진행 중 · 막힘 · 기한 임박 작업 수
- 안 한 요청이 붙은 작업의 **무게** — 하위 작업 수 · 걸린 안건 수 · 막힘 여부

방금 온 요청도 대기로 세므로 기간을 고를 때 끝을 오늘보다 조금 앞으로 두면 숫자가 덜 흔들린다 — 화면이 기본값으로 정할 일이다.

이걸로 사람마다 한 갈래를 붙인다.

| 갈래 | 규칙 (초안) | 뜻 |
| --- | --- | --- |
| **과부하** | 안 한 요청의 보낼 때 부하가 확인한 요청보다 뚜렷이 높다 · 또는 프로젝트 평균보다 높다 | 일이 많고 무거워서 놓친다 → 일을 나눠야 한다 |
| **단순 누락** | 부하가 평균 이하인데 확인율이 낮다 | 바빠서가 아니다 → 습관 · 배지를 못 보는 문제 |
| **특정 맥락** | 안 한 것이 한 파트 · 한 보낸 사람 · 안건 쪽에 몰린다 | 사람보다 요청이 오는 길의 문제 |
| **판단 보류** | 받은 수가 5건 미만 | 표본이 작아 갈래를 붙이지 않는다 |

### Claude 가 하는 것

관리 화면의 **[AI 분석]** — 리스크 AI 요약과 같은 틀(누를 때만 부르고 남기지 않는다).
위 숫자와 안 한 요청이 붙은 작업 · 안건의 제목 · 내용을 모아 **한 줄 총평 · 사람별 원인 · 손쓸 것** 으로 정리한다.

> 예: "확인율 62%. 박OO 님은 확인 안 한 4건 모두 진행 중 작업이 7개 넘을 때 왔다 — 과부하. HW-12 하위 작업을 나눌 만하다.
> 이OO 님은 부하가 평균 이하인데 5건 중 3건을 놓쳤다 — 배지를 못 보는 것인지 물어볼 것."

### 조심할 것

- **사람 평가 도구가 되면 안 된다.** 화면 말투를 '누가 못했나' 가 아니라 '어디에 일이 몰렸나' 로 쓴다. 갈래 이름도 사람이 아니라 상황을 가리킨다
- **보는 사람은 프로젝트 관리자, 그리고 자기 숫자는 본인** (Q39)
- 확인율은 **요청이 많이 온 사람에게 불리하다** — 받은 수를 늘 옆에 둔다

## 안 하는 것

- 홀로 보내는 쪽지 · 답 · 대화 · 읽음 표시 · 기한 · 다시 알리기 · 메일 · 슬랙 알림
- AI 가 대신 보내거나 사람을 점수 매기기
