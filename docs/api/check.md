# 확인 요청 — 합의 (2026-10-16, 2026-10-19 고침)

> 기획은 `docs/check-request-proposal.md`, 결정은 `docs/api/decisions.md` Q38 ~ Q41 · **Q42 ~ Q44**(닫힘).
> 이 파일은 **1차(요청 · 목록 · 확인 · 배지)** 의 계약이다. 확인율 분석(AX)은 기록이 쌓인 뒤 2차로 따로 세운다 — 아래 '2차'.
> 순서는 `server/PLAN.md` 11단계 · `web/PLAN.md` 12단계, 고친 것은 그 단계의 '2026-10-19 고침'.

**결정된 안건**에 붙는 **'이 결정 확인해 주세요' 버튼 하나**다. 쪽지가 아니다 — 내용 · 답 · 대화 · 읽음 · 기한 · 다시 알리기 · 수정 · 삭제가 없다.

> **2026-10-19 고침 (Q42 ~ Q44)** — 작업의 확인 요청을 걷었다. 안건이 **결정됐을 때만** 누르고, 내용을 적지 않고, 사람을 고르지 않는다.
> 받는 사람은 서버가 정한다 — **연결된 작업의 담당자 + 안건의 참조**. 한 결정에 **한 번**만 보낸다.

## 정해 둔 것

| | 결정 | 왜 |
| --- | --- | --- |
| 붙는 곳 | **안건 하나에 꼭** 붙고, 그 안건의 **그때 최근 결정**(`entryId`)에 묶인다 | 결정을 알리는 기능이다. 작업은 메신저 · 댓글이 맡는다 (Q42) |
| 누를 수 있을 때 | 안건이 `decided` 일 때만. 그 결정으로 **아직 안 보냈을 때만** — 결정을 바꾸면(`decide` · `change` 이력이 새로 남으면) 다시 보낼 수 있다 | 같은 결정을 두 번 알리면 확인율이 흐려진다 (Q44) |
| 받는 사람 | 서버가 정한다 — ① 이 안건에 **연결된 작업의 담당자**(작업 `seq` 순) ② 안건의 **참조**(`ccIds` 순). 겹치면 처음 자리 하나, **누른 사람은 뺀다**, 지금 이 프로젝트에 부여된 활성 멤버만(빠진 사람은 조용히 건너뛴다) | 결정이 영향을 주는 사람은 작업 담당자다. 그 밖에 알아야 할 사람은 참조로 붙여 둔다 (Q43) |
| 한 줄 = 한 사람 | 받는 사람 수만큼 **줄**이 생긴다. 한 번에 보낸 줄은 같은 `entryId` · `createdAt` 을 갖는다 | 상태가 사람마다 하나라 줄 하나가 곧 '보냄 → 확인' 이다 |
| 상태 | `confirmedAt` 이 `null` 이면 대기, 있으면 확인. **시간이 지나도 바뀌지 않는다** (Q40) | 두 상태뿐이다. 따로 `state` 를 두지 않는다 |
| 결정이 바뀌면 | 앞 결정의 대기 줄은 **그대로 둔다** (Q41 과 같은 뜻) | 확인한 것은 아니다. 새 결정은 새로 보낸다 |
| 걸린 것을 지우면 | 안건 · 이력을 지우면 요청도 같이 지운다(cascade) | 걸 데가 없는 요청은 뜻이 없다 |
| 보이는 범위 | **프로젝트 멤버 모두** 그 프로젝트의 요청을 본다. 보내기도 멤버 누구나 | 안건 상세에 '이 결정의 확인' 을 띄우려면 필요하다. 받은 것 · 보낸 것은 화면이 거른다 |
| 읽기 | **프로젝트의 요청 전부를 한 번에** — 거르기 · 정렬은 화면이 한다 | '집계는 프론트가 한다' (공통 규칙) |
| 배지 | 내 대기 수. 모든 프로젝트 합과 프로젝트별 (Q38) | 다른 프로젝트에 온 요청도 보여야 한다 |
| 보낼 때 부하 | 서버가 보내는 순간 받는 사람의 부하를 **같이 저장한다**. 응답에는 싣지 않는다 | 2차 분석의 바탕. 작업 상태 이력(`task_log`)이 없어 나중엔 되살릴 수 없다 |

## 참조 — `Thread.ccIds`

안건에 붙여 두는 **'결정을 같이 알아야 할 사람'**. 지금은 확인 요청을 받는 것 말고 하는 일이 없다.

- `Thread.ccIds: string[]` — 순서가 있다. 없으면 `[]` (`null` 아님, Q17)
- 안건 등록(`POST /api/projects/{projectId}/threads`) · 수정(`PATCH /api/threads/{threadId}`)에서 **통째로 바꾼다**. 안 보내면 그대로(수정) · `[]`(등록)
- 0 ~ 20명. 겹치면 처음 자리 하나로 합친다(개수는 합치기 전에 센다). 안건 담당자를 넣어도 된다
- 그 프로젝트에 부여된 활성 멤버만 — 아니면 400 **`MEMBER_NOT_IN_PROJECT`**, `detail` 은 걸린 자리 전부를 `{ "ccIds.N": "…" }` 로
- 스냅샷의 `threads` 에 같이 실린다(`snapshot.md`)

```
thread_cc
  thread_id · project_id  FK (thread_id, project_id) → thread(id, project_id) cascade
  member_id → member
  sort_order
  pk (thread_id, member_id)
```

## 테이블

```
check_request
  id · project_id → project(cascade)
  thread_id  FK (thread_id, project_id) → thread(id, project_id) cascade
  entry_id   → entry(id) cascade        -- 보낼 때 그 안건의 최근 decide · change 이력
  sender_id → member · recipient_id → member
  created_at · confirmed_at null 가능 · seq (Identity, unique)
  -- 보낼 때 받는 사람의 부하 (응답에 안 싣는다)
  load_open_tasks       그 프로젝트에서 받는 사람이 담당인 작업 중 완료 아닌 것
  load_blocked_tasks    그중 '막힘'
  load_due_soon_tasks   그중 기한(due)이 오늘(KST) + 3일 이하 — 이미 지난 것 포함
  load_open_threads     받는 사람이 담당인 안건 중 결정 안 된 것
unique (entry_id, recipient_id)
index (project_id, seq) · (recipient_id, confirmed_at)
```

- 2026-10-19 마이그레이션이 `task_id` · `text` 를 걷는다. **있던 줄은 지운다**(시드가 다시 넣는다) — 작업 줄은 걸 데가 없고, 안건 줄은 어느 결정에 묶을지 모른다
- 3일은 리스크의 기본 '기한 임박' 과 같은 값이다 — 프로젝트 리스크 기준을 따르지 않고 **고정**한다

export interface Thread {

## 엔드포인트

| 메서드 | 경로 | 하는 일 | 응답 |
| --- | --- | --- | --- |
| GET | `/api/projects/{projectId}/checks` | 그 프로젝트의 요청 전부, `seq` 오름차순(오래된 것 먼저) | `CheckRequest[]` |
| POST | `/api/threads/{threadId}/checks` | 보내기 — **본문 없음**(실어 와도 버린다). 받는 사람을 위 규칙으로 정하고 사람 수만큼 줄을 **한 트랜잭션**으로 만들며, 줄마다 부하를 찍는다. 보낸 사람은 로그인한 사람 | `CheckRequest[]` · 201 (받는 사람 순서) |
| POST | `/api/checks/{checkId}/confirm` | 확인. **받은 사람만** — 그 밖은 403 `FORBIDDEN`. 이미 확인했으면 그대로 돌려준다(멱등) | `CheckRequest` |
| GET | `/api/checks/pending-count` | 헤더 배지. 지금 부여된 프로젝트만 센다 | `CheckPendingCount` |

- 프로젝트 경계는 다른 API 와 같다 — `/api/threads/{threadId}/…` 는 안건의 프로젝트로, `/api/checks/{checkId}` 는 요청의 프로젝트로 본다(남의 것은 404)
- 보내기 검사 순서: 404 `THREAD_NOT_FOUND` → 400 `CHECK_THREAD_NOT_DECIDED` → 409 `CHECK_ALREADY_SENT` → 400 `CHECK_NO_RECIPIENTS`
- 동시에 두 번 눌러도 한 번만 들어간다 — 늦은 쪽은 `unique (entry_id, recipient_id)` 에 걸려 409 `CHECK_ALREADY_SENT`
- **수정 · 삭제 · 확인 취소는 없다**

| 상태 | `code` | 언제 |
| --- | --- | --- |
| 404 | `CHECK_NOT_FOUND` | 경로의 요청이 없음 (부여받지 않은 프로젝트의 요청도 같다) |
| 400 | `CHECK_THREAD_NOT_DECIDED` | 안건이 `decided` 가 아님 |
| 409 | `CHECK_ALREADY_SENT` | 그 안건의 최근 결정으로 이미 보냄 |
| 400 | `CHECK_NO_RECIPIENTS` | 받을 사람이 없음 — 연결 작업에 담당자가 없고 참조도 없거나, 나 하나뿐 |
| 400 | `MEMBER_NOT_IN_PROJECT` | 참조(`ccIds`)에 부여되지 않았거나 비활성인 사람 — 안건 등록 · 수정에서 |
| 422 | `VALIDATION_ERROR` | `ccIds` 가 20명 넘음 |
| 403 | `FORBIDDEN` | 받은 사람이 아닌데 확인 |

`CHECK_TARGET_NOT_FOUND` · `CHECK_RECIPIENT_SELF` 는 없어졌다.

## 구현에서 메운 것

- **확인은 받은 사람만** — 보낸 사람 · 시스템 관리자도 403. 시스템 관리자는 부여 없이도 보낼 수는 있다(다른 쓰기와 같은 경계)
- **대기 수** 는 시스템 관리자라도 부여된 프로젝트만 센다
- **최근 결정** — 그 안건의 `kind` 가 `decide` · `change` 인 이력 중 `seq` 가 가장 큰 것
- **부하** — 담당은 `owner_id`. 기한 임박은 `due <= 오늘(KST) + 3`, `due` 가 없는 작업은 안 든다. 셈은 `services/check.py` 의 `recipient_loads` 하나이고 시드도 이것을 쓴다
- **참조 검사는 새로 넣은 사람만** — 이미 참조에 있던 사람이 나중에 비활성 · 부여 해제돼도 그 사람을 그대로 둔 수정은 통과한다(담당자 · 파트 검사와 같다). 그런 사람은 보낼 때 조용히 빠진다
- **`ccIds` 오류 자리** — 걸린 id 가 겹쳐 있으면 겹친 자리까지 전부 `ccIds.N` 으로 싣는다
- **목업** — 화면에서 새로 만든 목업 안건도 같은 규칙(결정됨 · 한 번 · 받는 사람)을 목업 데이터로 따진다

## 화면 (프론트가 정할 것의 테두리)

- **작업 상세** — 확인 요청이 **없다**
- **안건 상세**
  - **참조** — 담당자 옆에 사람 칩 여럿 + 고르기(그 프로젝트의 활성 멤버). 고르면 바로 `PATCH`
  - **[확인 요청]** — 결정됨 · 이 결정으로 안 보냄 · 받을 사람이 있음, 셋 다일 때만 누를 수 있다. 버튼 곁에 '받는 사람 N명'(이름은 툴팁이나 펼침). **누르면 바로 보낸다** — 내용 입력 · 사람 고르기 창이 없다
  - 보낸 뒤에는 버튼 자리에 '이 결정 확인 2 / 3' 과 받는 사람 한 줄씩(이름 · 대기 / 확인 시각). 앞 결정의 묶음은 접어서 아래에
  - 못 누를 때 까닭을 한 줄로 — '결정된 안건만 보낼 수 있어요' · '이 결정은 보냈어요' · '받을 사람이 없어요 — 연결 작업 담당자나 참조를 더하세요'
- **왼쪽 메뉴 '확인 요청'** (`/checks`, 리스크 다음) — 탭 [받은 것 | 보낸 것]
  - 받은 것: 대기 먼저(오래된 순), 그다음 확인(최근 확인 순). 줄마다 안건 칩(누르면 상세) · 결정 한 줄(`Entry.text`) · 보낸 사람 · 보낸 날 · **[확인]**
  - 보낸 것: 최근 순, **한 번에 보낸 묶음(`entryId`)이 한 줄** — 안건 칩 · 결정 한 줄 · 확인 N / M · 펼치면 사람별 대기 / 확인(시각)
- **배지** — 메뉴 '확인 요청' 옆에 지금 프로젝트의 내 대기 수, 프로젝트 고르기에 다른 프로젝트 수. 0 이면 안 그림
- **다시 받기** — 목록은 `/checks` 에 들어올 때 · 안건 상세를 열 때 · 내가 보내거나 확인한 뒤. 배지는 앱이 뜰 때 · 창에 포커스가 돌아올 때 · 60초마다
- [내 파트 \| 전체] 는 따르지 않는다

## 2차 — 확인율 분석 (아직 계약 아님)

기획의 'AX' 절. 기록이 몇 주 쌓인 뒤 이 파일에 계약을 더한다. 테두리만 적어 둔다.

- `GET /api/projects/{projectId}/checks/stats?from=&to=` — 사람별 받은 수 · 확인 수 · 확인율 · 확인까지 걸린 시간 중앙값 · 대기와 확인의 보낼 때 부하 비교 · 갈래(과부하 · 단순 누락 · 특정 맥락 · 판단 보류). 프로젝트 관리자는 전부, 그 밖은 자기 줄만 (Q39)
- 갈래는 **규칙**이 붙이고, [AI 분석] 은 리스크 AI 요약과 같은 틀(SSE, 누를 때만, 남기지 않음)
- 받는 까닭(작업 담당 · 참조)은 줄에 남기지 않았다 — 분석에 필요하면 2차에서 `reason` 칸을 더한다
